# 2.2.7 进阶 · 从 C 代码到芯片里的二进制

> **一句话本质：芯片只认 0/1。编译 = 把你的代码"翻译"成机器码，再把所有东西的地址"定下来"。**
>
> 这一篇不要求你会写编译器，只要求你**看到报错时知道它发生在哪一步**。

---

## 一、一条流水线

```
  你写的             预处理        编译        汇编         链接         格式转换
chassis.c  ──>  chassis.i  ──>  chassis.s  ──>  chassis.o  ─┐
                                                            ├─> firmware.elf ──> firmware.bin
main.c     ──>  main.i     ──>  main.s     ──>  main.o     ─┤                      │
                                                            │                      ▼
                            startup_stm32xxx.s ─────────────┤                烧录进芯片 Flash
                            厂商库 / 数学库 ────────────────┘                （CPU 上电从这里开始跑）
```

| 步骤 | 干什么 | 产物 | 典型的报错长这样 |
|---|---|---|---|
| **预处理** | 处理所有 `#` 开头的行：把 `#include` 内容**原文插进来**、`#define` 替换、`#if` 裁剪 | `.i` | `fatal error: motor.h: No such file or directory` |
| **编译** | 检查语法/类型，做优化，翻译成汇编 | `.s` | `error: expected ';' before '}'` |
| **汇编** | 把汇编翻译成机器码，但**地址还没定**（不知道别人在哪，也不知道自己烧到哪） | `.o` | —— |
| **链接** | 把一堆 `.o` + 库**拼起来**，给每个函数/变量分配地址，把"调用 xxx"的坑填上 | `.elf` | `undefined reference to 'Motor_SetSpeed'`（找不到实现）<br>`multiple definition of ...`（定义了多份） |
| **格式转换** | 用 `objcopy` 从 `.elf` 里抽出纯数据 | `.bin` / `.hex` | —— |
| **烧录** | J-Link 把 `.bin` 写进 Flash | —— | —— |

**一句话记住两件事：**

- 编译阶段**只管自己的 `.c`**，所以别人的函数你"只要声明"就能调用（2.2.2）。
- 链接阶段才是"把所有东西装进一台机器"的时间——**名字重复、名字找不到，都是这一步爆的**。

## 二、链接脚本：谁规定了 Flash / RAM 的边界

链接器靠**链接脚本**（`.ld` 文件）知道：

```ld
MEMORY
{
    FLASH (rx) : ORIGIN = 0x08000000, LENGTH = 512K   /* 代码放这里 */
    RAM  (rwx) : ORIGIN = 0x20000000, LENGTH = 128K   /* 变量放这里 */
}
```

你**不用背**它，但要知道它的存在：**"RAM 不够用"、"Flash 写满"这类问题，答案都在这里。**

## 三、代码在内存里分成几段（看这一段，两个困惑就解开了）

| 段 | 放什么 | 存在哪 |
|---|---|---|
| `.text` | 代码、常量 | Flash |
| `.data` | **有初值**的全局 / 静态变量 | 初值存在 Flash，上电时**拷到 RAM** |
| `.bss` | **没写初值或初值为 0** 的全局 / 静态变量 | 只占 RAM，不占 Flash |
| 栈（stack） | 局部变量、函数调用现场 | RAM |
| 堆（heap） | `malloc` 出来的东西（嵌入式能不用就不用） | RAM |

于是你就能回答两个经典困惑：

1. **为什么复位以后，全局变量自动是 0？**
   因为启动文件（`startup_xxx.s`）在跳进 `main` 之前，把 `.bss` 段**整块清零**、把 `.data` 段从 Flash 拷到 RAM。
   而**局部变量在栈上，没人替它清零** → 值随机（对应 2.2.3 那条坑）。

2. **为什么 RAM 不够会崩？**
   全局变量吃掉 `.data` + `.bss`，剩下给栈的不多；函数调用太深或局部数组太大 → **栈溢出** → 踩坏别的变量 → 表现成"玄学 bug"。
   排查手段之一：看 `.map` 文件（链接器输出的清单，谁占了多少空间一目了然）。

## 四、"我点了一下 Build 按钮"到底发生了什么

```
Build  = 依次跑：预处理 → 编译 → 汇编 → 链接 → objcopy
Download/Flash = J-Link 把 bin 写进 Flash
Reset  = CPU 从 Flash 起始地址取第一条指令 → 启动文件 → main
```

所以：

- **改了代码没重新 Build 就烧录** → 烧的还是旧的（现象：改了没效果，实习生最常见的"灵异事件"）。
- **`undefined reference`** → 函数写了，但那个 `.c` 没加进工程、或没参与编译。
- **`multiple definition`** → 同一个变量/函数被定义了两次（回去看 2.2.2 头文件那节）。

## 五、想亲手看一眼（可选，做了印象极深）

在 MSYS2 终端里，对着一份最简单的 `.c` 依次执行：

```bash
arm-none-eabi-gcc -E  test.c -o test.i      # 预处理：打开 test.i，看 include 被"撑开"成什么样
arm-none-eabi-gcc -S  test.c -o test.s      # 编译：看 C 变成了什么汇编
arm-none-eabi-gcc -c  test.c -o test.o      # 汇编：得到目标文件
arm-none-eabi-objdump -d test.o             # 反汇编：看机器码和汇编的对应关系
```

看完 `test.i` 的体积，你就再也不会觉得 `#include` 是"引用"了。
