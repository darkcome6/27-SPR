# 2.2.2 c 文件与 h 文件的关系

> **一句话本质：`.h` 是目录（声明），`.c` 是正文（实现）。**
> 别人要用你的功能，只需要看"目录"，不需要看"正文"。

---

## 一、先记住一个反直觉的事实

**`#include` 不是"引用"，而是"复制粘贴"。**

编译之前有个**预处理**阶段，它会把 `#include "motor.h"` 这一行**原地删掉，换成 `motor.h` 的全部内容**。
所以：

- `.h` 里写什么，就会被**原样塞进每一个** include 它的 `.c` 文件里。
- `.h` 里不该放的东西（函数体、变量定义）会因此被复制多份 → 链接时报 `multiple definition`。

（预处理还会做 `#define` 文本替换、`#if` 条件裁剪，见 2.2.8。）

---

## 二、为什么要拆成两个文件

因为**编译是以 `.c` 为单位的**：

```
motor.c ──编译──> motor.o ─┐
main.c  ──编译──> main.o  ─┼──链接──> firmware.elf ──> firmware.bin
uart.c  ──编译──> uart.o  ─┘
```

`main.c` 编译的时候，**根本没见过 `Motor_SetSpeed` 的函数体**。
它只需要知道一件事："有这么个函数，参数长这样，返回这个东西"——这个信息就在 `.h` 里。
真正的函数体由**链接器**在最后一步去别的 `.o` 里找到地址、接上。

这就是**声明（declaration）与定义（definition）**的区别：

| | 声明 | 定义 |
|---|---|---|
| 作用 | 告诉编译器"有这个东西，长这样" | 真正分配内存 / 生成代码 |
| 例子 | `void Motor_SetSpeed(uint8_t id, int16_t speed);` | 带 `{ ... }` 的那个函数本体 |
| 位置 | 放 `.h` | 放 `.c` |

## 三、一个最小例子：拆出电机模块

```c
/* ---------------- motor.h ---------------- */
#ifndef MOTOR_H          /* 头文件保护，见 2.2.8 */
#define MOTOR_H

#define MOTOR_NUM        4               /* 宏：纯文本替换 */
#define MOTOR_MAX_SPEED  1000

typedef struct {                         /* 类型定义：谁要用谁得看见 */
    int16_t speed;
} Motor_t;

extern Motor_t motor[MOTOR_NUM];         /* 变量声明：定义在 motor.c 里 */

void Motor_SetSpeed(uint8_t id, int16_t speed);   /* 函数声明 */
int16_t Motor_GetSpeed(uint8_t id);

#endif
```

```c
/* ---------------- motor.c ---------------- */
#include "motor.h"      /* 必须包含自己的头，保证声明与定义一致 */

Motor_t motor[MOTOR_NUM];    /* 真正的定义：这里才分配内存 */

void Motor_SetSpeed(uint8_t id, int16_t speed)
{
    if (id >= MOTOR_NUM) return;             /* 边界检查：C 不会替你拦 */
    if (speed > MOTOR_MAX_SPEED)  speed =  MOTOR_MAX_SPEED;
    if (speed < -MOTOR_MAX_SPEED) speed = -MOTOR_MAX_SPEED;

    motor[id].speed = speed;
    /* 真正写寄存器 / 发 CAN 报文 ... */
}

int16_t Motor_GetSpeed(uint8_t id)
{
    return (id < MOTOR_NUM) ? motor[id].speed : 0;
}
```

```c
/* ---------------- main.c ---------------- */
#include "motor.h"      /* 只要"目录"，不要"正文" */

int main(void)
{
    Motor_SetSpeed(0, 500);
    return 0;
}
```

## 四、什么东西该放哪

**判断标准只有一条**（就是第二节那张"声明 vs 定义"表的落地版）：

> **这行代码在内存里占了地方、或者会变成机器码吗？**
> 会 → 放 `.c`　·　不会（只是"描述"或"打招呼"）→ 放 `.h`

**为什么是这个标准？** 回到第一节的机制：**`.h` 会被原样复制进每一个 include 它的 `.c`**。
所以往 `.h` 里写东西，就等于"让每个文件都抄一份"：

| 抄的是什么 | 复制多份的后果 |
|---|---|
| **描述**（"有这么个函数，收两个 int16_t"） | 无所谓 —— 每份内容都一样 |
| **实体**（"这里给我分配 4 个字节"） | 每个文件都分了一块 → **符号重复** → 链接报 `multiple definition` |

下面逐条对照。

### ① 函数声明 → `.h`｜函数体 → `.c`

```c
/* ---- motor.h：声明，只告诉编译器"有这么个函数" ---- */
void Motor_SetSpeed(uint8_t id, int16_t speed);
```

```c
/* ---- motor.c：定义，真正的机器码在这里 ---- */
void Motor_SetSpeed(uint8_t id, int16_t speed)
{
    /* 函数体 ... */
}
```

- **声明为什么必须放 `.h`**：`main.c` 编译时根本没见过这个函数，全靠 `.h` 告诉它"有这么个东西、参数长这样"。没有这句，编译器**没法检查你调用得对不对**（C99 之后连调用都不允许）。
- **函数体为什么必须放 `.c`**：函数体会**生成机器码**，是一个实打实的符号。放进 `.h`，被 3 个 `.c` include 后就有了 3 份同名机器码 → 链接器报 `multiple definition of 'Motor_SetSpeed'`。
  **这一条一定会报错，没有例外。**

### ② `#define` 宏、常量 → `.h`

```c
/* ---- motor.h ---- */
#define MOTOR_NUM        4
#define MOTOR_MAX_SPEED  1000
```

- 宏是**预处理阶段的纯文本替换**，编译器根本看不到它 → **不占内存、不产生符号** → 复制多少份都无害。
- 放 `.h` 才是对的：所有文件用同一个值，改一处全场生效。
- ⚠️ 代价是宏**没有类型、没有作用域、不参与任何检查**。写 `#define MOTOR_NUM 4;`（末尾多打个分号）能让你查一下午 —— 所以宏别乱用（见 2.2.8）。

### ③ `typedef` / 结构体 / 枚举的**类型定义** → `.h`

```c
/* ---- motor.h ---- */
typedef struct {
    int16_t speed;
} Motor_t;
```

- 类型定义是**编译期的图纸**，编译完就没了 → 不占内存、不产生符号 → 放 `.h` 安全。
- **⚠️ 这里是最容易翻车的地方**：`struct` 的**类型定义**和**变量定义**长得太像了：

```c
typedef struct { int16_t speed; } Motor_t;   /* 类型图纸：放 .h ✅ */
Motor_t motor[MOTOR_NUM];                    /* 真实变量，占 8 字节：放 .c ✅ */
```

> 同一个 `struct` 分两处写。所以"结构体放 `.h`"这句话，**只对前半句成立**。

### ④ `extern` 变量声明 → `.h`｜变量定义 → `.c`

```c
/* ---- motor.h：打个招呼，"有这么个数组，别处定义了" ---- */
extern Motor_t motor[MOTOR_NUM];
```

```c
/* ---- motor.c：真正占地，"这里给我 8 个字节" ---- */
Motor_t motor[MOTOR_NUM];
```

**区别就是一个关键词 `extern`：**

| 写法 | 是什么 | 占内存吗 | 放哪 |
|---|---|---|---|
| `extern int x;` | 声明 | ❌ 不占 | `.h` |
| `int x;` | 定义 | ✅ 占 | `.c` |
| `int x = 0;` | 定义（带初值） | ✅ 占 | `.c` |

- **为什么需要 `extern`**：`uart.c` 想用 `motor.c` 里的 `motor[]`，得先知道它存在、是什么类型。`extern Motor_t motor[MOTOR_NUM];` 就是这句"打个招呼"。
- ⚠️ **一个很阴的特例**：中间那行 `int x;`（不带 `extern`、也不带初值）在 C 里叫 **暂定定义（tentative definition）**。**有些编译器会把多份静默合并成一个、不报错**（gcc 10 之前默认如此）。

  于是你会遇到："我在 `.h` 里写了变量，居然编译过了？"
  **过了不等于对。** 两个 `.c` 里改的其实是**同一个变量**，A 改了 B 也跟着变 —— 这类 bug 比"直接报错"难查一万倍。
  而带初值的 `int x = 0;` 是正式定义，**新旧编译器都一定报** `multiple definition`。

  > **实测（gcc 6.3.0）**：把 `int g_x;` 写进 `.h`、两个 `.c` 都 include → **编译链接通过，退出码 0**（静默合并）。换成 `int g_y = 5;` → 立刻报 `multiple definition of 'g_y'`。
  >
  > **口诀：变量定义永远放 `.c`，不要用"编译器报不报错"来判断对错。**

### ⑤ `static` 的函数和变量 → `.c`

```c
/* ---- motor.c ---- */
static int32_t s_enc_offset;         /* 只有本文件用得上的中间变量 */

static void clamp_speed(int16_t *v)  /* 只有本文件用得上的工具函数 */
{
    /* ... */
}
```

- `static`（写在函数外）的意思是：**"这东西只给我这个文件用"**。既然只给自己用，就不需要别人看见 → 自然不放 `.h`。
- **⚠️ 反过来更危险**：把 `static` 变量写进 `.h`，被 3 个 `.c` include 后：

```c
/* ---- bad.h ---- */
static int counter = 0;   /* 每个 include 它的 .c 都各拿到一份独立的 counter！ */
```

  它**不会报重复定义**（`static` 是内部链接），但你会得到 **3 个互不相干的 `counter`** —— 你在 A 文件里加 1，B 文件里还是 0。你以为在共享一个计数器，其实各玩各的。

  > **实测（gcc 6.3.0）**：`.h` 里写 `static int counter = 0;`，两个 `.c` 都 include，编译**不报错**；运行起来是：
  >
  > ```text
  > a.c 里的 counter -> 地址 00407020  值 7
  > b.c 里的 counter -> 地址 00407024  值 0
  > ```
  >
  > 两个地址不一样 —— 它们确实是两个变量：a.c 改成了 7，b.c 里还是 0。

### ⑥ 特例：`const` 常量放哪？

新手最常见的想法是"常量嘛，当然放 `.h` 共享"。但在 **C 语言里 `const` 变量默认是外部链接**（这点和 C++ 相反）：

```c
/* ---- bad.h ---- */
const int MOTOR_MAX = 1000;   /* 这是个"定义"！每个 include 它的 .c 都来一份 → 重复定义 */
```

想要"大家都用的常量"，正经写法有这几种：

| 写法 | 放 `.h` 安全吗 | 说明 |
|---|---|---|
| `#define MOTOR_MAX 1000` | ✅ | 纯文本替换，不占内存（最常用） |
| `enum { MOTOR_MAX = 1000 };` | ✅ | 编译期整型常量，不占内存，**而且有类型检查** |
| `static const int MOTOR_MAX = 1000;` | ✅ | 每个 `.c` 各一份只读副本，合法，但**每份都占内存** |
| `const int MOTOR_MAX = 1000;` | ❌ | 重复定义 |

> **建议**：整数常量优先用 `enum` —— 它比 `#define` 安全（参与类型检查，也没有"多打个分号"那种坑）。

### 速查表

| 东西 | 放哪 | 一句话理由 |
|---|---|---|
| 函数声明 | `.h` | 只是打招呼，不产生机器码 |
| 函数体 | `.c` | 产生机器码，放 `.h` 必报重复定义 |
| `#define` 宏 | `.h` | 纯文本替换，不占内存 |
| `typedef` / `struct` / `enum` 的**类型定义** | `.h` | 编译期图纸，不占内存 |
| `extern` 变量声明 | `.h` | 只是打招呼 |
| **变量定义**（含结构体变量） | `.c` | 占内存，放 `.h` 会重复定义 |
| `static` 函数 / 变量 | `.c` | 只给本文件用 |
| 整数常量 | `.h`（用 `#define` 或 `enum`） | 编译期常量，不占内存 |
| `const` 变量的定义 | `.c` | C 里 `const` 默认外部链接，放 `.h` 会重复定义 |
| `static inline` 函数 | `.h`（可以） | 内联展开，不产生独立符号（进阶，见到不奇怪） |

### 三处最容易翻车的地方

1. **把结构体变量跟着结构体类型一起写进了 `.h`**（见 ③）
2. **靠"编译器没报错"判断变量定义的位置对不对**（暂定定义会被静默合并，见 ④）
3. **把 `static` 变量写进 `.h`** —— 不报错，但每个文件各拿到一份副本（见 ⑤）

## 五、常见坑

1. **在 `.h` 里写函数体 / 变量定义**
   → 每个 include 它的 `.c` 都生成一份 → 链接报 `multiple definition of ...`
2. **`.c` 忘了 include 自己的 `.h`**
   → 声明和定义不一致，**编译器不会报错**，出错时在别的文件里报，极其难查。（养成"`.c` 第一行就 include 自己的 `.h`"的习惯。）
3. **头文件互相 include**
   → 无限套娃。靠头文件保护宏兜住（见 2.2.8）。
4. **把 `.h` 当"公共变量堆放处"**
   → 所有人 include 就拿到所有全局变量，代码越写越乱（07 章会专门整治）。
