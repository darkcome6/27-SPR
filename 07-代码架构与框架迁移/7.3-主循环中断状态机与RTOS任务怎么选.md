# 7.3 · 主循环、中断、状态机、RTOS 任务怎么选

> 不是"上了 RTOS 就高级"，而是"这几件事真的必须同时进行吗"。
> 先把工作排清楚，再决定用什么装它。

## 这一节在干什么

把 7.1 需求清单里的每件工作，安排到具体的执行位置：
主循环？定时器中断？状态机？RTOS 任务？

**这一节不讲代码，只画时序。**画不清楚，代码一定乱。

## 先列清楚：到底有几件事在跑

校内赛底盘（示范）：

| 工作 | 什么时候发生 | 最晚多久得处理 | 能不能等 |
|---|---|---|---|
| 蓝牙来数据 | 随时，不确定 | 别把串口缓冲撑爆 | 能等一小会儿 |
| 解算 + 输出 | 固定周期（比如 5 ms） | 必须准时 | **不能等** |
| 读 IMU | 固定周期 | 可以慢一点 | 能等 |
| 失联检测 | 持续计时 | 500 ms 内必须停车 | **不能等** |
| 打印调试 | 想打就打 | 无所谓 | 能等 |

> 判断标准就一句话：**"能不能等"和"最晚多久"。**
> 凡是"不能等"的，才需要抢占；凡是"能等"的，塞主循环里就行。

## 第一步：从最朴素的写法开始

```
while (1)
{
    read_imu();
    calc_and_output();
}
```

能跑，但有两个洞：
1. **不准时** —— `read_imu()` 慢一点，控制周期就跟着飘
2. **等不起** —— 蓝牙数据来了没人收，缓冲一满就丢

**先别急着上 RTOS，先把洞补上。**

## 第二步：加定时器中断，把"不能等"的事挑出来

```
TIM 中断（每 5 ms）：解算 + 输出     ← 准时，谁也拦不住
while (1)：读 IMU、打印、处理其他杂事  ← 慢一点没关系
串口中断：收蓝牙帧，只丢进缓冲       ← 中断里只做最少的事，别解算
```

到这里，绝大多数校内赛项目**已经够了**。

> 💡 中断里只干"收下、标记"这种最轻的活。
> 在中断里做浮点解算、串口打印，就是在给自己埋坑 —— 卡住别的工作不说，还会拖垮整个时序。

## 第三步：用状态机表达"流程"

"上电自检 → 待机 → 运行 → 故障"这类**顺序流程**，用 `switch-case` 状态机写，一目了然：

```
上电自检 → 待机 → 运行 → 故障
                 ↑___________|
```

状态机解决的是"**现在该干什么**"，定时器中断解决的是"**什么时候干**"，两件事别混。

## 什么时候才轮到 RTOS

同时满足这几条，再考虑上 RTOS：

- 有**多件"不能等"的工作**，而且它们的周期各不相同、互相阻塞
- 用主循环 + 中断已经写出了"到处是标志位、互相等"的结构，**改不动了**
- 你算过 RAM：FreeRTOS 本身和每个任务的栈都要吃内存，**F103C8T6 只有 20 KB**

一旦用了 RTOS，下面这些就**变成你的责任**：

| 问题 | 后果 |
|---|---|
| 任务优先级定错 | 该准时的任务不准时 |
| 共享数据不加保护 | 数据偶尔出错，而且**极难复现** |
| 高优先级任务一直等低优先级的锁 | 优先级反转，系统卡死 |
| 忘了喂看门狗 | 板子反复复位 |

> ⚠️ 能用主循环 + 中断解决的事，就不要引入 RTOS。
> **"能少一个变量就少一个变量"，在时序设计上同样成立。**

## 共享数据：中断和主循环之间的那道缝

只要中断和主循环都碰同一个变量，就必须交代清楚：

- 用 `volatile` 告诉编译器"这个值随时会变"
- 多字节变量（比如 `float`）读一半被中断改掉，会读到**拼不起来的数**
- 要改就一次改完，必要时关中断保护

> 这些坑不会每次都出现，只会在赛场上偶尔出现 —— 这才是最难受的。

## 交付物

1. **运行时序图 / 任务表** —— 每件工作：在哪儿执行、多久一次、最晚多久
2. **共享数据清单** —— 谁写、谁读、怎么保护
3. **选择理由** —— 为什么用主循环 + 中断，或者为什么必须上 RTOS

## 验收标准

- [ ] 随机指一件工作，能说出它在哪儿执行、为什么
- [ ] 能指出至少一处共享数据，并说明怎么保护
- [ ] 如果上了 RTOS：能说出每个任务的优先级，以及为什么这么排
- [ ] 如果没上 RTOS：能说清"哪几个条件满足了我才会上"
