# 7.5 · 通信层与传感器驱动：从字节流到有效数据

> 传感器给你的从来不是"数据"，是**字节流**。
> 把它变成 `vx`、`vy`、`ω`，是你这一层的活。

## 这一节在干什么

让数据能**可靠地**从外面进来：建链 → 解包 → 校验 → 出错处理，最后交给上层的是**有物理含义的量**。

做完你会知道：为什么加第二个传感器时，控制算法一行都不用改。

## 第一步：先设计帧，再写代码

蓝牙（或任何串口设备）传过来的是连续字节。你会遇到：

- 丢了一个字节 → 后面**全错位**
- 一次收到半帧，或者两帧粘在一起
- 干扰产生的乱码

所以要先定一个"能自己找回同步"的格式（示范）：

```
┌────────┬────────┬──────────┬────────┬────────┐
│ 帧头1  │ 帧头2  │  长度     │  载荷   │ 校验和 │
│ 0xAA   │ 0x55   │ payload  │ vx vy ω│  XOR   │
└────────┴────────┴──────────┴────────┴────────┘
```

| 字段 | 为什么要有 |
|---|---|
| 帧头 | 让接收方知道"一帧从哪儿开始" |
| 长度 | 让接收方知道"还要收多少字节" |
| 校验 | 让接收方判断"这帧是不是好的" |
| 载荷 | 真正的数据 |

> 帧格式是**双方约定**的，遥控端和底盘必须用同一份定义。
> 改格式 = 两边一起改，所以要写下来（协议文档），别只在脑子里。

## 第二步：用状态机解包，而不是"一次收完"

解包的正确姿势是**一个字节一个字节地喂状态机**：

```
等帧头1 → 等帧头2 → 等长度 → 收载荷 → 校验 → 交付给上层
  ↑                                          │
  └──────────── 校验失败 / 超时 ──────────────┘
```

好处：哪怕中间夹杂乱码、丢了一字节，状态机也能**自己走回起点**，而不是从此永远错位。

> 💡 中断里只做"把收到的字节丢进缓冲"。
> 解包放到主循环里做 —— 中断越短，系统越稳。

## 第三步：把"没数据"也当成一种状态

数据链路里，**"没有数据"是必然会发生的**，不是意外：

| 情况 | 你希望程序怎么做 |
|---|---|
| 500 ms 没收到有效帧 | 认为失联 → 停车 |
| 收到帧但校验失败 | 丢掉，不影响上一份有效值，计数上报 |
| 长时间一帧都没有 | 上电自检失败 / 提示 |

> 7.1 里那条 `REQ-T-01`（断连 500 ms 停车），实现位置就在这里。

## 第四步：不同传感器，不同的解包，同一个终点

现实中的传感器接口五花八门，但目标一样：**变成有物理含义的量**。

| 来源 | 拿到的形式 | 解包要做的事 |
|---|---|---|
| 蓝牙 / 串口设备 | 字节流 | 找帧头、验长度、校验和 |
| IMU（I2C/SPI） | 寄存器里的原始值 | 读寄存器、拼高低字节、减去零偏、换算 |
| 编码器 | 定时器计数值 | 读计数、算增量、换成转速 |

**手段不同，终点相同：上层拿到的是 `vx/vy/ω`、姿态角、转速。**

> 这就是为什么加第二个传感器不用改控制算法 ——
> 因为算法只认"姿态角"，不关心它是 MPU6050 给的还是别的芯片给的。

## 一条铁律

**上层代码里不许出现这些：**

- ❌ `0xAA`、帧头、校验和 —— 这是通信层的私事
- ❌ 寄存器地址、`0x68` 之类的器件地址 —— 这是驱动的私事
- ❌ 原始字节数组、`HAL_UART_Receive` —— 这是 BSP 的私事

上层只该看见：`imu_angle`、`target_vx`、`link_ok` 这类**有含义的量**。

> 检查方法很简单：搜索一下，看这些词有没有漏到 `App/`、`Control/` 里。

## 交付物

1. **通信协议文档** —— 帧格式、字段含义、单位、量程、发送周期
2. **可用的收发 + 解包代码** —— 至少一种串口设备打通
3. **异常处理记录** —— 拔线、发乱码、发半帧，各是什么现象

## 验收标准

- [ ] 现场发一帧合法数据，上层能拿到正确的值
- [ ] 现场发乱码 / 半帧，程序不崩、不错位，能自己恢复
- [ ] 拔掉通信线 500 ms，程序进入约定的失联处理
- [ ] 上层代码里搜不到帧头常量、寄存器地址
