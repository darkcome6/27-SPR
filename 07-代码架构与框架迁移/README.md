# 07 · 代码架构与框架迁移

> 围绕校内赛任务，从需求出发，一步步设计、实现、验证一个完整的电控项目，再亲手完成芯片和传感器迁移。

## 本章不是先讲术语，而是带着做项目

新手很难只听“要分层、低耦合、高内聚”就理解架构的价值。本章从[校内赛任务分析](../06-校内赛引言/校内赛的任务分析.pdf)出发，所有课程共同完成一个项目：先弄清机器要完成什么，再决定用什么硬件、怎样安排程序、代码如何分工，最后把系统跑通。

每一步都留下设计结果，并回答一个实际问题：**如果需求、芯片或传感器变了，哪些地方应该跟着改，哪些地方不应该被牵连？**

## 项目实施路线

1. **先读任务，写清需求**：从校内赛任务中提取输入、输出、动作流程、响应时间、精度和异常情况；将“看起来能做”变成可检查的功能与验收条件。
2. **再选资源，画出硬件方案**：本轮先以 STM32F103C8T6 为目标控制器，根据项目需要盘点 GPIO、定时器/PWM、ADC、串口、I2C/SPI、中断和 DMA 等资源；列出要控制的执行机构、要读取的传感器及其接口，并检查引脚、外设和性能是否够用。
3. **决定工作如何运行**：按控制周期、传感器更新频率和通信时序，安排主循环、定时中断和状态机；只有确实需要并行处理、且能说明时序需求时，才引入 RTOS 任务。明确任务优先级、共享数据和资源保护，不把“用了多线程”当成架构目标。
4. **搭建芯片与板级基础**：用 CubeMX 配置时钟、引脚和外设，生成并验证基础工程；将板级引脚映射、外设句柄和基础初始化收口到 BSP。CubeMX 生成代码是工程起点，BSP 是项目维护的板级接口，两者职责不要混为一谈。
5. **接通通信与传感器数据**：为不同传感器整理通信接口和帧格式，在对应驱动/协议模块完成收发、解包、校验和错误处理；向上提供含义清楚的数据，不让控制逻辑直接依赖原始字节或某个传感器的寄存器细节。
6. **实现用户逻辑和控制算法**：根据任务流程组织应用状态机；将控制算法作为独立逻辑，以传感器数据为输入、执行机构指令为输出。通过明确接口连接 BSP、驱动/协议、算法和应用流程，并完成联调、边界条件和故障处理验证。
7. **做迁移演练，验证边界是否有效**：替换一种传感器，再将项目迁移到另一款芯片或芯片库。记录实际改动的模块、需要重新验证的行为，以及架构没有隔离好的地方；目标是复用稳定的业务逻辑和算法，而不是承诺换平台完全不改代码。
