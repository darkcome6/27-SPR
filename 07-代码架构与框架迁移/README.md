# 07 · 代码架构与框架迁移

> 从“代码能跑”走到“改得动、查得清、换得了”。

## 为什么要学架构

新手刚开始写程序，通常一个文件、几个全局变量就能把功能做出来。这没有错：先做出能运行的东西，才有东西可以改。

麻烦出现在下一次改动：想换一个传感器，结果控制逻辑、驱动和参数到处都要改；想修一个 bug，却不确定会不会影响别的功能；队友接手后，也很难看出“改这里会影响哪里”。项目越大，这些修改和排查的成本就越高。

**架构不是为了把代码拆得越细越好，而是为了让每次改动尽量只影响该改的地方。**它关系到项目后续开发有多快、能接住多复杂的需求，也决定了换芯片、换库时要付出多大代价。

## 新手怎么学：先做改动，再总结方法

不要一开始就要求新手背“分层、解耦、内聚”。先从 02 里的 demo 出发，让它跑起来，再给它几个真实的改动任务：

1. **先改功能，记录代价**：例如调整一个参数或替换一种外设，看看要改几个文件、哪些地方容易漏、改完要重新验证什么。
2. **再整理代码边界**：把“负责操作硬件的代码”和“决定要做什么的逻辑”分开，通过清楚的接口交互。改动时观察影响范围有没有缩小。
3. **最后再给经验起名字**：把“一个职责放在一处”“模块通过接口协作”“硬件变化不应迫使业务逻辑跟着重写”等经验，分别对应到模块化、分层和低耦合。

每一步都比较整理前后的改动范围。**学架构不是为了代码看起来更专业，而是为了下一次改需求时少改、少漏、容易验证。**

## 先分清两件事

- **代码怎么组织**：模块和层之间如何分工、通过什么接口协作。这决定代码改起来是否容易，裸机和 RTOS 项目都需要考虑。
- **程序怎么运行**：主循环、状态机或 RTOS 任务如何安排工作。这决定工作何时执行、如何共享资源，是运行时调度问题。

它们有关联，但不是一回事。本章先从代码组织和改动边界入手，再讨论什么时候需要状态机或 RTOS；不是把程序拆成多个线程，就自动得到了好架构。

## 课程清单

| 文件 | 主题 | 交付件 / 验收 |
|---|---|---|
| 7.1 | 从“能跑”到“改得动”：改动范围就是架构的体感 | 给 02 的 demo 增加一个需求，记录修改点、遗漏风险和验证步骤 |
| 7.2 | 把职责和接口理清：模块化不是为了多建文件 | 将一项功能收进模块，通过明确接口使用；说明数据由谁拥有、谁可以修改 |
| 7.3 | 硬件变了，业务尽量不动：从例子理解分层 | 把 02 的 demo 按硬件操作、业务规则和应用流程划分，并完成一次外设替换 |
| 7.4 | 哪些值该改配置，哪些逻辑该改代码 | 将易变参数集中管理，通过统一接口读取并验证 |
| 7.5 | 先看工作怎么运行：裸机状态机还是 RTOS 任务 | 用同一组功能说明选择依据；实现一个协同 demo，并检查共享资源和故障处理 |
| 7.6 | 换芯片 / 换库时，怎样把改动限制在边界内 | 做一次平台迁移演练，列出改动文件并验证业务行为不变 |

> 线程（RTOS 任务）不是“代码模块”的另一种叫法。优先级、共享资源、优先级反转和看门狗属于运行时协同问题；根据 demo 的需要逐步引入，不要求新手为了用 RTOS 而用 RTOS。
