# 7.6 · 用户逻辑、控制算法与整机联调

> 用户逻辑决定"**做什么**"，控制算法决定"**怎么做到**"。
> 这两件事混在一段代码里，就是项目失控的开始。

## 这一节在干什么

把前面几层串起来，跑通完整链路：

```
蓝牙 → 解包 → 目标速度 → 运动学解算 → 限幅 → 4 路占空比 → 电机
```

并且能说清：**7.1 的每一条需求，落在了哪一层。**

## 第一步：应用逻辑用状态机写

底盘从上电到跑起来，是一串**流程**：

```
上电自检 ──失败──→ 故障
    │成功
    ↓
  待机 ──收到指令──→ 运行 ──失联/出错──→ 故障
    ↑                  │
    └──────收到停止─────┘
```

每个箭头都要有条件，写清楚：

| 迁移 | 条件 |
|---|---|
| 自检 → 待机 | IMU 能读到、姿态合理 |
| 待机 → 运行 | 收到有效遥控帧 |
| 运行 → 故障 | 失联超时 / 自检项丢失 |
| 故障 → 待机 | 人工复位，不能自己恢复 |

> ⚠️ **故障状态为什么不能自动恢复？**
> 如果你不知道当初为什么坏，自动恢复只是让它再坏一次 —— 而且这次带着速度。

## 第二步：控制算法单独成一层

运动学解算的本质是一个**纯计算**：

```
输入：vx, vy, ω          （想要什么）
输出：4 个轮子的目标转速   （每个轮子该怎么转）
```

它有两条重要性质：

1. **不碰硬件** —— 里面没有 GPIO、没有 HAL、没有电机
2. **不碰全局变量** —— 给什么算什么，算完返回

> 好处很实在：这种函数可以**在电脑上直接跑**，喂几组数就知道对不对，
> 不用连着整车调试。换芯片、换电机时它也完全不受影响。

限幅也放在这一层（对应 `REQ-S-01`）：

```
if (解算结果超出最大转速)
    全部轮子等比缩小   ← 不是每个轮子各自削顶
```

> 各自的削顶会**破坏速度方向的比例**，车走出来的轨迹是弯的。
> 这就是为什么需求里要专门写一条"整体等比缩放"。

## 第三步：把需求、模块、代码对上号

画一张表，检查有没有需求"无家可归"：

| 需求 | 落在哪一层 | 在哪个文件 |
|---|---|---|
| 收到有效帧后解算轮速 | 通信层 + 控制层 | `comm_uart.c` → `chassis_kinematics.c` |
| 断连 500 ms 停车 | 应用层 | 主循环里的失联判断 |
| 超限等比缩放 | 控制层 | `chassis_kinematics.c` |
| 上电自检 | 应用层 + 驱动层 | 状态机 + `imu_driver.c` |

> **有需求找不到归属，说明还漏了一段代码。**
> 反过来，有代码找不到对应需求，那可能是你自己加戏了。

## 第四步：联调要分步，别一次全开

一次把整条链打开，出了问题你根本不知道是谁的错。按这个顺序上：

| 步骤 | 只做什么 | 应该看到 |
|---|---|---|
| 1 | 只读不写：打印 IMU 姿态 | 晃动板子，数字跟着动 |
| 2 | 只写不读：手动设固定占空比 | 四个轮子按预期转 |
| 3 | 半条链：蓝牙 → 解包 → 打印 | 打印出正确的 `vx/vy/ω` |
| 4 | 全链路上台架：蓝牙 → 解算 → 限幅 → 电机 | 轮子按指令的比例转 |
| 5 | 加保护：拔蓝牙、拔传感器 | 车停住 / 报警，不疯跑 |
| 6 | 上车实测 | 完成 7.1 里定的任务 |

> 每一步都要留下**现象证据**（串口打印 / 波形 / 视频）。
> 口头说"我试过了"，不算。
