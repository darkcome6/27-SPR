# 7.7 · 迁移演练：换传感器、换芯片

> 迁移不是"重写一遍"，而是**验证你画的那条边界，到底有没有用**。
> 这一节就是这一整章的答案：架构好不好，看改动范围就知道。

## 这一节在干什么

对同一个项目做两次替换：

1. **换一个传感器** —— 比如把 IMU 换成另一款，或者把蓝牙换成另一条链路
2. **换芯片 / 换库** —— 换到另一款 MCU，或者从标准库换到 HAL

然后**数文件**：到底改了几个、为什么必须改。改得越少，前面几节做得越对。

## 演练 A：换传感器

**做之前先预测**：你觉得要改哪些文件？写下来。

**做完之后对照**：

| 期望改动的 | 不该动的 |
|---|---|
| 驱动文件（新器件的寄存器操作） | 运动学解算 |
| 通信/解包文件（如果帧格式不同） | 应用状态机 |
| BSP 里对应的接口实现 | 限幅、失联判断 |
| 协议文档 | 主循环时序 |

> 如果发现**算法里也要改**，那就是 7.5 的边界没守住：
> 十有八九是原始字节、寄存器地址漏进了 `Control/` 或 `App/`。

## 演练 B：换芯片 / 换库

换芯片动的应该是"贴硬件最近"的那一层：

| 期望改动的 | 不该动的 |
|---|---|
| CubeMX 工程（引脚、时钟、外设） | `App/`、`Control/`、`Comm/` |
| `BSP/` 的实现（HAL 调用、句柄） | 运动学、PID 的公式 |
| 启动文件、链接脚本 | 状态机、需求对应的业务规则 |

> 最理想的情况：`Control/` 一个字节都不用动。
> 因为运动学只认 `vx/vy/ω`，它根本不认识 STM32。

## 记录表（这一节的核心交付物）

每改一个文件，都记一笔：

| 文件 | 改了什么 | 为什么必须改 | 判定 |
|---|---|---|---|
| `bsp_motor.c` | 引脚映射 | 硬件接线变了 | ✅ 合理 |
| `chassis_kinematics.c` | 加了 if 判断传感器类型 | 想省事 | ❌ 边界没划好 |
|  |  |  |  |

最后一列的判定只有两种：

- ✅ **合理** —— 确实贴着硬件，本来就该改
- ❌ **返工** —— 说明这块东西被放错了位置，**记下来，回头修正**

> ⚠️ 出现 ❌ 不是失败。**这一节的目的就是把它找出来。**
> 新手常见的心态是"能跑就行了，不想动"，而这里正是"改动范围"这件事第一次变得**看得见**。

## 回归验证：换完还要证明没坏

改完一定要把 7.1 的验收清单重跑一遍：

- [ ] 正常链路：发指令 → 轮子按比例转
- [ ] 失联保护：拔通信线，500 ms 内停车
- [ ] 自检：拔掉传感器，程序能发现
- [ ] 限幅：给超量程目标，轮速保持比例
- [ ] 数据流：整条链路的现象和迁移前一致

> **"换完能跑"和"换完行为没变"是两件事。**
> 只测了正常链路，等于没测。

## 交付物

1. **改动清单** —— 上面那张记录表，含 ✅/❌ 判定
2. **迁移后的可运行工程**
3. **回归验证记录** —— 每一项的现象证据
4. **一句话结论**：这次迁移，架构帮你省下了多少工作

## 验收标准

- [ ] 两次替换都完成，工程能跑
- [ ] 能说出"哪些文件本来不该改"，以及它暴露了什么问题
- [ ] 回归验证全部重跑，有证据
- [ ] 能回答整章的核心问题：**为什么架构比算法更影响一个项目的上限？**

---

## 回到 7.1 的那个问题

现在你应该能自己回答开篇那句话了：

> **架构不是为了把代码拆得细，而是为了让每次改动只影响该改的地方。**

回看 7.1 你写下的需求清单 —— 每一条需求，从赛题一路走到验收，中间经过的每一层都清清楚楚。
这才是"代码超过一千行也不乱"的真正含义：

**不是文件多、目录深，而是你随时能说清：改这里，会影响哪里。**
