## 〇、这本教材的灵魂（动笔前必读）

### 0.1 表象之下是机制

新生看到的，是一个函数。你要让他看到的，是函数背后的**一整条链**。

> **标准示范** —— 写一个"置高电平"函数，背后发生了什么？

表象（一个调用）：
```c
HAL_GPIO_WritePin(GPIOB, GPIO_PIN_0, GPIO_PIN_SET);   // 让 PB0 输出高电平
```

**往下挖到"能解释机制"就够了**（这是达标线，不是天花板）：
1. **API 层**：这个函数不是魔法，它最终只做一件事——往一个"和引脚对应的寄存器"里写一个值。
2. **寄存器 / 硬件层**：芯片里每个引脚都对应一组寄存器，写特定寄存器 = 控制这个引脚输出高低。CPU 把值写进寄存器 → 内部电路传到引脚 → 引脚变高 → LED 亮。


**示范的分寸感（重要）：**
- 深度不够 = 打发（只给函数不给机制，语法糖）❌
- 深度太深 = 劝退（一上来就晶体管物理 / 寄存器竞态）❌
- **合适的深度 = 让新生"哦，原来是这样"**：讲清"函数背后是寄存器、是手册"这一层就达标，

### 0.2 我们培养的不是"仅仅会调库的人"更是调库之外的东西

每一章都该指向这四种能力：
1. **独立思考** —— 遇到没见过的知识，能够迅速了解背后的运行机制，而非关注表面的语法糖。
2. **自己诊断问题** —— bug 不可怕，可怕的是不会分析问题，不具备快速高效解决问题的能力。
3. **形成自己的思维体系** —— 意识到自己学的东西从GPIO到通讯到控制器都是围绕机器人展开的。
4. **善于利用工具** —— AI、手册、调试器、示波器都是手的延伸；会用工具的人，走得远。

### 0.3 态度：前辈的严谨、慎重与热爱

- **严谨**：你写下的每个字新生会当真。技术细节自己先验证，别把错的教给别人。
- **慎重**：拿不准就标"存疑"并去查证，不猜、不糊弄。
- **热爱**：写自己真正觉得酷的东西。热爱会传染，凑合不会。

### 0.4 尊重新生的时间 = 尊重自己的时间

- 一句话能讲清的，绝不用一段话；一段话的，绝不用一页。
- 每一段都要有**信息量**，灌水是对读者最大的不尊重。
- 排版清晰、路径明确。读者省下的时间，就是你的时间。

## 三、写作红线

1. **语法糖禁令**：只给 API 不给机制 = 不合格。`为什么` 永远优先于 `怎么做`。
2. **名词不解释 = 不合格**：首次出现必须有一句话形象解释。
3. **不能是纯步骤流水账**：每一步都要有"为什么"。
4. **先体感后理论**：先让 LED 亮、电机转，再上规范。规范是痛苦的解药，不是额外负担。
6. **AI 内容必须验证**：AI 生成的代码 / 结论，自己先验证验证
7. **不教"怎么办"**：教提问三段式——"发生了什么 / 我做了什么 / 我猜是什么原因"。

## 四、如何教"思考与诊断"

### 4.1 分析问题的能力
- **先稳定复现，再动手改**：偶发 bug 复现不了 = 没有证据。
- **结合已知条件，分析问题**：砍掉一半可能性，缩小真凶范围。
### 4.2 提问三段式
所有答疑、所有文档里的"问与答"，都按"发生了什么 / 我做了什么 / 我猜是什么原因"引导。没有排查记录的提问，电控组不受理。

### 4.3 工具怎么教
- **查手册**：教快速定位法（框图 → 寄存器表 / 功能说明 → 时序图），不是从头读。
- **用 AI**：教"如果…那么…"式的提问、教交叉验证、教它当"第二大脑"而不是"作业代写机"。

## 六、Git / GitHub 协作（VSCode 版）

仓库：`https://github.com/darkcome6/27-SPR.git`（默认分支 `main`）

### 6.1 先说人话：分支 / 主干是干什么的

**main（主干 / 主分支）** = 项目的"正式版"。这是大家公认的那一份，谁都能看，但谁都不能在上面随手乱改。想象它是已出版的教材：可以修订，但不能随便涂鸦。

**分支（branch）** = 从主干上"叉"出去的一条工作线，像树枝。
- 机制上它不是复制品，只是一个"指向某次提交的标签"——所以建分支几乎不占空间。
- 你在自己的分支上随便改，**不影响主干，也不影响别人**。
- 改完，把分支"接回"主干 = 合并（merge / PR），Git 会做差异比对，把你改的部分合进去。

**为什么一个人时可以推 main，多人时必须用分支？**
- 一个人：没人和你抢，推 main 永远安全。
- 多人：都直接推 main，两人同时改同一个文件 → 后推的人要么覆盖别人、要么报冲突，乱成一锅粥。
- 分支 + PR = 给每个人一块独立的"工作间"，互不打扰，最后统一"验收合并"。

**PR（Pull Request）到底是什么？**
- 你推完分支，在 GitHub 上发起"申请把我的分支合并进 main"。
- 它是一个**验收关口**：别人能看到你改了什么、能评论、确认没问题才合并。
- 对咱们团队：就是"写完让负责人看一眼，再进正式版"。

**首次**：装 Git → VSCode 登录 GitHub → `Ctrl+Shift+P` → `Git: Clone` → 粘贴地址 → 配置身份：
```bash
git config --global user.name "你的名字"
git config --global user.email "你的邮箱"
```

**日常**：
```bash
git pull                            # 1. 先拉最新，别在旧版上改
git checkout -b 02-toolchain        # 2. 建自己的板块分支
git add 02-第一台能"动"的机器/
git commit -m "docs(02): 完成工具链配置讲义"
git push -u origin 02-toolchain     # 3. 推送
```
→ GitHub 上 New pull request 合并到 `main` → `git checkout main && git pull`

- 提交规范：`docs(02): 描述`、`fix(03): 描述`；写清"改了什么、为什么"，别写 `update`、`111`。
- 冲突：VSCode 里处理 `<<<<<<< ======= >>>>>>>` 标记，保留两边都对的部分。
- 红线：别推大二进制（docx / xlsx 用文本模板）；别 `push -f`；提交前看 `git status`。
